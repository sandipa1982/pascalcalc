# PascalCalc — Backend Coding Prompts: 05 HTTP API

**Phase:** 4 — Backend Implementation  
**Component:** 05 HTTP API  
**Provenance:** Reconstructed prompts based on approved designs and inspected source; not evidence of original prompt execution.

## Purpose and scope

Implement transport-layer handlers for Arithmetic, Math and Expression only after the underlying domain logic is complete.

## Prerequisites and dependencies

- Approved [Solution Approach](../../../Docs/SOLUTION_APPROACH.md), [System Architecture](../../../Docs/architecture.md), and [Backend HLD](../../../Docs/backend-hld.md).
- Go module `calculator-app/backend` and Project Foundation completed.
- Work in an isolated development workspace; do not modify the original project.
- Requires components 01–04: API constants, configuration, arithmetic, math and expression evaluator.

## Main Coding Prompt — P04-05-01

**Type:** Reconstructed main coding prompt

> Act as a senior Go backend engineer implementing PascalCalc. Follow the approved Phase 1–3 design documents and completed prerequisite components. Generate source in dependency order in an isolated workspace. Do not modify the original PascalCalc project.
> 1. Create `internal/arithmetic/handler.go`, `internal/mathops/handler.go`, and `internal/expression/handler.go`.
> 2. Define the request and response structs used by each handler: arithmetic and math operands `a` and `b` as JSON numbers, and expression `{ "expression": "..." }`. Success responses use `result`; expression success includes `expression` and `result`; errors use `{ "error": "..." }`.
> 3. Register exact versioned paths from `internal/api/routes.go`: arithmetic add/subtract/multiply/divide, math power/sqrt/percentage, and expressions/evaluate. Allow POST only and return method-not-allowed otherwise.
> 4. Apply configured maximum request bytes with `http.MaxBytesReader`, decode one JSON object with unknown fields rejected, reject trailing JSON, validate required operands, and validate arithmetic finite operands/results.
> 5. Math sqrt requires `a` only; power and percentage require both `a` and `b`. Preserve domain error messages and JSON content type. For expression, trim whitespace, reject empty or invalid UTF-8, create a fresh evaluator per request and apply configured 1024-byte expression limit.
> 6. Keep handlers independent of service process startup, Nginx and Docker. Use dependency injection for arithmetic/math services and config. Do not invent new endpoints.
> 7. Output source and actual compilation evidence if run.

## Unit Testing Prompt — P04-05-02

**Type:** Reconstructed unit-testing prompt

> Act as a Go unit-test engineer. Use the code generated by the immediately preceding main coding prompt, not the original tests as a template.
> 1. Create `internal/arithmetic/handler_test.go`, `internal/mathops/handler_test.go`, and `internal/expression/handler_test.go` using `net/http/httptest` as isolated handler unit tests.
> 2. Exercise every route and method, valid JSON, missing fields, unknown fields, malformed/trailing JSON, oversized body, division by zero, invalid math domain, blank expression and 1024/1025-byte expression boundaries.
> 3. Assert response status, JSON keys and errors; do not start external servers, gateway or containers.
> 4. Run `go test ./internal/arithmetic ./internal/mathops ./internal/expression` with coverage if available; record observed output.

## Code Review Prompt — P04-05-03

**Type:** Reconstructed code-review prompt

> Act as a principal Go code reviewer. Use the newly generated implementation and tests and the approved design as review inputs.
> 1. Review HTTP contract fidelity, status codes, content type, JSON decoding, request-size controls, domain error propagation and per-request evaluator isolation.
> 2. Check handler unit-test completeness and compare behavior to existing handlers. Flag math non-finite JSON encoding as a possible gap only if evidence supports it.
> 3. Produce evidence-based findings; do not edit the original project.
