# PascalCalc — Backend Coding Prompts: 02 Arithmetic


## Purpose and scope

Implement the reusable arithmetic business-logic component after Project Foundation. This component implements addition, subtraction, multiplication, and division using Go `float64` values. It does not implement HTTP routes, JSON handling, API handlers, service startup, or Docker configuration; those are addressed by later components.

## Prerequisites and dependencies

- Approved `Docs/SOLUTION_APPROACH.md`, `Docs/architecture.md`, and `Docs/backend-hld.md`.
- Component 01 project foundation, including module `calculator-app/backend`.
- Go toolchain compatible with the existing `backend/go.mod`.
- No dependency on the Math or Expression services.

**Implementation sequence:** arithmetic service → service unit tests → code review. HTTP handlers are addressed separately in Component 05.

## Main Coding Prompt — P04-02-01

**Type:** Reconstructed main coding prompt

> Act as a senior Go backend developer implementing the Arithmetic domain component for PascalCalc. Use the approved Phase 1–3 design documents and the completed Project Foundation. Work in the isolated backend development workspace; do not modify the original PascalCalc project during documentation validation.
>
> 1. Create `backend/internal/arithmetic/service.go` in package `arithmetic`.
> 2. Define a stateless `Service` type and a `NewService() *Service` constructor.
> 3. Implement `Add(a, b float64) float64`, `Subtract(a, b float64) float64`, `Multiply(a, b float64) float64`, and `Divide(a, b float64) (float64, error)`.
> 4. For division by zero, return an error with the message `cannot divide by zero`; do not panic or silently return infinity.
> 5. Keep calculation logic independent of `net/http`, JSON, configuration, Nginx, and other domain services. Do not add HTTP handlers or route registration in this step.
> 6. Preserve Go's `float64` arithmetic semantics. Do not invent rounding, decimal precision, or overflow policies beyond the approved design; record any unspecified behavior for review.
> 7. Show the generated file, implementation decisions, and local build/format commands. Report observed build results only if commands are actually run.

**Expected source mapping:** `backend/internal/arithmetic/service.go`.

## Unit Testing Prompt — P04-02-02

**Type:** Reconstructed unit-testing prompt

> Act as a Go unit-test engineer. Use the implementation generated by P04-02-01. Create `backend/internal/arithmetic/service_test.go` using Go's standard `testing` package, with table-driven tests where appropriate.
>
> 1. Test all four operations with positive, negative, and zero operands.
> 2. Test subtraction operand order, multiplication by zero, division producing a fraction, and division by zero, including the expected error message.
> 3. Add appropriate floating-point boundary and special-value cases where the design defines behavior; distinguish unspecified `NaN`/infinity behavior from defects.
> 4. Test the service directly without HTTP requests, routers, external services, or mocks that are not needed.
> 5. Run `go test ./internal/arithmetic` and `go test -cover ./internal/arithmetic` from `backend/` if the environment permits. Record actual pass/fail and coverage results; never invent them.
> 6. Do not alter implementation code merely to make tests pass without approval.

**Expected unit-test mapping:** `backend/internal/arithmetic/service_test.go`.

**Scope note:** `handler_test.go` is an existing source file but is mapped to Component 05 — HTTP API. It is not a required output of this component's unit-testing prompt.

## Code Review Prompt — P04-02-03

**Type:** Reconstructed code-review prompt

> Act as a principal Go engineer. Review the source generated by P04-02-01 and unit tests generated by P04-02-02 against the approved design and existing PascalCalc arithmetic service.
>
> 1. Check the four operation signatures, statelessness, arithmetic correctness, division-by-zero behavior, and error wording.
> 2. Check package cohesion and absence of HTTP, configuration, Math, or Expression dependencies.
> 3. Review unit-test coverage of positive, negative, zero, fractional, and error paths; inspect assertions and test isolation.
> 4. Review floating-point limitations, including non-finite results, and distinguish domain behavior from validation that belongs in the HTTP handler.
> 5. Compare generated files with the original `internal/arithmetic/service.go` and `service_test.go` for behavioral equivalence rather than byte-for-byte identity.
> 6. Produce a checklist, file-to-prompt mapping, observed command results, coverage evidence if available, and findings categorized as Pass / Partial / Fail / Not verified. Recommend changes but do not modify original source without approval.

**Expected output:** `P04-02-03_CODE_REVIEW.md` in the isolated validation workspace.
