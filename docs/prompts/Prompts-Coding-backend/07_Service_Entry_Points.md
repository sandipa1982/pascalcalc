# PascalCalc — Backend Coding Prompts: 07 Service Entry Points

**Phase:** 4 — Backend Implementation  
**Component:** 07 Service Entry Points  
**Provenance:** Reconstructed prompts based on approved designs and inspected source; not evidence of original prompt execution.

## Purpose and scope

Create the independently runnable Go executables after service routers and runtime support are complete.

## Prerequisites and dependencies

- Approved [Solution Approach](../../../Docs/SOLUTION_APPROACH.md), [System Architecture](../../../Docs/architecture.md), and [Backend HLD](../../../Docs/backend-hld.md).
- Go module `calculator-app/backend` and Project Foundation completed.
- Work in an isolated development workspace; do not modify the original project.
- Requires component 06 and all three domain HTTP handlers; no new domain logic.

## Main Coding Prompt — P04-07-01

**Type:** Reconstructed main coding prompt

> Act as a senior Go backend engineer implementing PascalCalc. Follow the approved Phase 1–3 design documents and completed prerequisite components. Generate source in dependency order in an isolated workspace. Do not modify the original PascalCalc project.
> 1. Create `backend/cmd/arithmetic-api/main.go`, `backend/cmd/math-api/main.go`, `backend/cmd/expression-api/main.go` and retain `backend/cmd/api/main.go` for the legacy combined server.
> 2. Each main delegates to `server.Run` with its own service router and default port: Arithmetic 8081, Math 8082, Expression 8083, and legacy 8080.
> 3. On startup errors log a fatal error and exit nonzero. Do not duplicate configuration loading, route registration, or calculation logic inside main.
> 4. Ensure each executable can be built separately (`go build ./cmd/arithmetic-api`, etc.); avoid overwriting output binaries when running build commands.
> 5. Do not add Nginx or Docker Compose changes here; these are deployment phase concerns. Return source and observed command output only if executed.

## Unit Testing Prompt — P04-07-02

**Type:** Reconstructed unit-testing prompt

> Act as a Go unit-test engineer. Use the code generated by the immediately preceding main coding prompt, not the original tests as a template.
> 1. Unit-test startup wiring where feasible without invoking `main()` or calling `log.Fatal`; verify the router selection and default ports by inspecting or testing extracted pure wiring only if the existing design exposes it.
> 2. Do not create artificial `main_test.go` files that merely duplicate static source assertions. If direct unit tests are not meaningful for thin main wrappers, explicitly record that unit-test coverage is provided by Component 06 router tests and that build checks are required.
> 3. Run `go test ./cmd/...` and independent `go build -o <temporary-path> ./cmd/<service>` where possible; record real outcomes. No Docker, gateway or end-to-end tests.

## Code Review Prompt — P04-07-03

**Type:** Reconstructed code-review prompt

> Act as a principal Go code reviewer. Use the newly generated implementation and tests and the approved design as review inputs.
> 1. Review all four entry points for correct default ports, router wiring, startup failure handling, no duplicated logic, and independent buildability.
> 2. Confirm unit-test limitations are accurately described, and compare generated entry points with original code.
> 3. Report findings and command evidence, without changing existing application code.
