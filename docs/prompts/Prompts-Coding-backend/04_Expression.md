# PascalCalc — Backend Coding Prompts: 04 Expression



## Purpose and scope

Implement the tokenizer and stateful expression evaluator using already completed Arithmetic and Math services, with a 1024-byte backend expression limit.

## Prerequisites and dependencies

- Approved [Solution Approach](../../../Docs/SOLUTION_APPROACH.md), [System Architecture](../../../Docs/architecture.md), and [Backend HLD](../../../Docs/backend-hld.md).
- Go module `calculator-app/backend` and Project Foundation completed.
- Work in an isolated development workspace; do not modify the original project.
- Requires completed Arithmetic (`02`) and Math (`03`) calculation services; do not call them over HTTP.

## Main Coding Prompt — P04-04-01

**Type:** Reconstructed main coding prompt

> Act as a senior Go backend engineer implementing PascalCalc. Follow the approved Phase 1–3 design documents and completed prerequisite components. Generate source in dependency order in an isolated workspace. Do not modify the original PascalCalc project.
> 1. Create `backend/internal/expression/tokenizer.go` and `backend/internal/expression/evaluator.go` in package `expression`.
> 2. Tokenize ASCII decimal numbers, `+`, `-`/`−`, `*`/`×`, `/`/`÷`, `^`, parentheses, postfix `%`, and square root `√` or `sqrt`, plus whitespace. Define token types and EOF; reject unsupported characters and malformed numeric literals.
> 3. Implement `Evaluator` with token cursor, `*arithmetic.Service`, `*mathops.Service`, and `maxExpressionLength`; constructors `NewEvaluator()` and `NewEvaluatorWithLimit(int)`.
> 4. Reject input when `len(input)` exceeds 1024 by default (UTF-8 bytes); return `expression too long`. Do not conflate this with the frontend 256-character limit.
> 5. Implement precedence, parentheses, unary signs, right-associative exponentiation, square root, and postfix percentage with recursive-descent methods. Reuse the arithmetic/math services directly, propagate division-by-zero and square-root errors, and reject trailing tokens and non-finite results.
> 6. Evaluator has mutable parser state: instantiate per request, or explicitly document why sharing is unsafe. No HTTP handlers or JSON in this component.
> 7. Return complete source and actual build results only if executed.

## Unit Testing Prompt — P04-04-02

**Type:** Reconstructed unit-testing prompt

> Act as a Go unit-test engineer. Use the code generated by the immediately preceding main coding prompt, not the original tests as a template.
> 1. Create `backend/internal/expression/tokenizer_test.go`, `backend/internal/expression/evaluator_test.go`, `backend/internal/expression/sqrt_expression_test.go`, and `backend/internal/expression/length_validation_test.go`.
> 2. Cover token variants, whitespace, malformed numbers, unsupported symbols, parentheses, precedence, associativity, unary signs, percentage, square root, division by zero, and invalid results.
> 3. Test 1024 and 1025 **UTF-8 bytes**, including multibyte characters, separately from frontend 256 characters. Test default and configurable evaluator limits.
> 4. Test repeated evaluation and state reset; note evaluator is not concurrency-safe for shared use.
> 5. Run `go test ./internal/expression` and `go test -cover ./internal/expression` when possible. Do not write handler or integration tests.

## Code Review Prompt — P04-04-03

**Type:** Reconstructed code-review prompt

> Act as a principal Go code reviewer. Use the newly generated implementation and tests and the approved design as review inputs.
> 1. Review tokenizer grammar, parser termination, precedence/associativity, error paths, byte-length enforcement and reuse of domain services.
> 2. Inspect test coverage for boundary and maliciously deep expressions; record resource-exhaustion risks without changing original code.
> 3. Compare generated source and tests with the existing implementation and record observed evidence and discrepancies.
